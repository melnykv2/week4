# Django sample app - Terraform + Ansible + AWS SSM

This project deploys the Django healthcheck sample application with Terraform and configures it with Ansible over AWS Systems Manager Session Manager.

## Architecture

```text
Internet
   |
   v
Public ALB :80
   |
   +-------------------+
   |                   |
   v                   v
Private EC2 #1      Private EC2 #2
Nginx :80           Nginx :80
Gunicorn :8000      Gunicorn :8000
   |                   |
   +---------+---------+
             |
             v
      Private PostgreSQL EC2
          :5432

Private subnets -> NAT Gateway -> Internet
                           |
                           +--> GitHub / Ubuntu repositories / AWS APIs

Ansible -> AWS SSM -> EC2
```

## Requirements

- AWS credentials configured locally.
- Terraform >= 1.6.
- Ansible.
- AWS Session Manager Plugin.
- Ansible `amazon.aws` and `community.postgresql` collections.
- A fork of `https://github.com/kaaalim/django-sample-app`.

Install the collections:

```bash
ansible-galaxy collection install amazon.aws community.postgresql
```

The Ubuntu 24.04 AMI is an AWS-provided AMI with SSM Agent preinstalled. Terraform only verifies/starts the preinstalled agent; it does not download a second agent.

## 1. Fork the application

Fork `https://github.com/kaaalim/django-sample-app` and set your fork URL when applying Terraform:

```bash
terraform -chdir=terraform init
terraform -chdir=terraform apply \
  -var='app_repo_url=https://github.com/YOUR_USERNAME/django-sample-app.git'
```

## 2. Deploy infrastructure

```bash
terraform -chdir=terraform fmt -recursive
terraform -chdir=terraform validate
terraform -chdir=terraform plan
terraform -chdir=terraform apply
```

Terraform creates:

- one VPC;
- two public subnets;
- two private subnets;
- an Internet Gateway;
- a NAT Gateway for private subnet outbound access;
- two private web EC2 instances;
- one private PostgreSQL EC2 instance;
- a public ALB;
- security groups for ALB, web and DB;
- an EC2 IAM role with `AmazonSSMManagedInstanceCore`;
- an S3 bucket for the Ansible SSM connection plugin;
- encrypted SSM Parameter Store values for DB password and Django secret;
- an Ansible inventory file at `ansible/inventory.ini`.

No EC2 instance has a public IP and no SSH is required.

## 3. Run Ansible

Terraform generates the inventory with the EC2 instance IDs. The playbooks use `amazon.aws.aws_ssm` as their connection, so Ansible executes through Systems Manager rather than SSH.

Configure the database first:

```bash
ansible-playbook -i ansible/inventory.ini ansible/db.yml
```

Configure both web servers:

```bash
ansible-playbook -i ansible/inventory.ini ansible/webservers.yml
```

Deploy the application:

```bash
ansible-playbook -i ansible/inventory.ini ansible/deploy.yml
```

Or run all three in this order as separate commands.

## 4. Test

```bash
terraform -chdir=terraform output -raw alb_dns_name
```

Open:

```text
http://<ALB-DNS-NAME>/
```

## Important notes

- The DB password and Django secret are generated by Terraform and stored as SSM `SecureString` parameters.
- Ansible reads the secrets from Parameter Store at deployment time.
- Do not commit `terraform.tfstate`, `.terraform/`, `ansible/inventory.ini`, or application `.env` files.
- The Ansible SSM plugin requires the local AWS credentials to have S3 access to its temporary module-transfer bucket. The EC2 instance itself does not need S3 credentials for this plugin.

## Why SSM is used

The EC2 instances are private and have no SSH access. The AWS-provided Ubuntu 24.04 AMI already contains SSM Agent. Terraform attaches `AmazonSSMManagedInstanceCore` and starts the preinstalled agent. Ansible then uses the `amazon.aws.aws_ssm` connection plugin.

The plugin uses an S3 bucket to transfer Ansible modules. The generated inventory contains the bucket name and EC2 instance IDs, so no private IP/SSH key is needed for the Ansible connection.
